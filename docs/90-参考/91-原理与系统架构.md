# 3DS 破解原理与系统内部构造（导读）

本仓库其他文档回答的是"怎么做"：怎么破解、怎么备份、怎么装游戏。这篇回答"为什么"：3DS 的系统是如何构成的，为什么信任链会断，为什么现在的破解流程长成这个样子。

定位是**中文导读 + 权威链接索引**：正文只讲清核心概念和它们与折腾的关系，细节一律指向 [3dbrew.org](https://www.3dbrew.org/wiki/Main_Page)（3DS 破解社区维护的技术 wiki，英文）。文中所有 3dbrew 链接均为逐条核实过的真实页面。阅读本篇前建议先过一遍 [术语表](../00-新手上路/03-术语表.md)。

## 一、为什么 3DS 能被破解：信任链与漏洞

### 双处理器安全设计

3DS 的 SoC 里有两颗主要处理器，职责刻意分开（详细硬件分析见 [Copetti 的 3DS 架构文章](https://www.copetti.org/zh-hans/writings/consoles/nintendo-3ds/)，有中文版）：

| 处理器 | 角色 | 跑什么 |
| --- | --- | --- |
| **ARM9** | 安全世界（Secure World） | 密钥管理、NAND/Title 安装、加密运算等系统服务；游戏无权直接访问 |
| **ARM11**（MPCore，多核） | 应用世界（Application World） | 系统模块、HOME 菜单、游戏，开发者能接触到的全部 |
| ARM7TDMI | 隐藏协处理器 | 只在 DS/GBA 兼容模式下工作，与破解关系不大 |

安全模型设想很美好：游戏（ARM11 userland）即使被攻破，也碰不到密钥和系统数据，因为那些都在 ARM9 手里。**破解的本质，就是设法拿到 ARM9 的控制权**——一旦做到，全盘加密形同虚设，这就解释了为什么所有现代折腾工具（GodMode9 等）都以"ARM9 权限下运行的 FIRM"形式存在。

### 启动链：从按下电源键到 HOME 菜单

参考：[3dbrew - Bootloader](https://www.3dbrew.org/wiki/Bootloader)、[3dbrew - FIRM](https://www.3dbrew.org/wiki/FIRM)。

```
BootROM（Boot9 + Boot11，固化在芯片内，不可更新）
  └─ 校验 NAND 分区表（NCSD 头）的 RSA 签名
      └─ 校验并加载 firm0/firm1 分区的 FIRM（系统固件镜像）
          ├─ ARM9 侧：Kernel9（内核）→ Process9（唯一的 ARM9 用户态进程，系统服务核心）
          └─ ARM11 侧：Kernel11（内核）→ 系统模块（sm / fs / pm / loader / pxi 等）
              └─ PM 启动 NS → HOME 菜单 → 游戏
```

每一层都用 RSA 验签保证只加载任天堂签名的代码，这就是信任链（Chain of Trust）。链条的根是 **BootROM**——它存在芯片掩模里，出厂后无法改写、无法通过系统更新修补。这个"不可更新"在当年是安全卖点，日后恰恰成了致命的弱点。

### 信任链是怎么断的

公开披露的漏洞清单见 [3dbrew - 3DS System Flaws](https://www.3dbrew.org/wiki/3DS_System_Flaws)，大体分两类：

| 类别 | 作用位置 | 代表 | 能做什么 |
| --- | --- | --- | --- |
| **入口漏洞**（userland） | ARM11 应用层 | 浏览器漏洞（super-skaterhax）、系统设置漏洞（MSET9）、SSL 模块漏洞（SSLoth）、游戏/服务漏洞（nimdsphax 等） | 在用户态跑自制代码（Homebrew Launcher），再借提权漏洞接触 ARM9 |
| **引导漏洞**（bootrom 层） | 启动最早期 | BootROM 的 RSA 验签缺陷（**sighax**，由 BootROM 被硬件手段导出后发现） | 让 Boot9 加载任意伪造签名的 FIRM，开机即获得 ARM9 控制权 |

理解"入口 vs 引导"的区别，就理解了现代破解流程为什么是三明治结构：

- **入口漏洞只是"进门的钥匙"，会失效**：任天堂可以通过系统更新修补用户态漏洞，super-skaterhax 之前一代代入口（ninjhax、soundhax、SeedMiner……）都随版本更新被换掉。它本身不等于破解成功。
- **boot9strap（B9S）才是"房子本身的产权"**：B9S 利用 sighax 把自制引导代码写进 NAND 的 FIRM 分区，**替换在 BootROM 验签之后、官方系统启动之前**的位置。BootROM 的验签缺陷永远无法修复，所以 B9S 一旦装上，任何系统版本、任何后续更新都拿它没办法。
- 标准流程 [破解流程](../00-新手上路/01-破解流程.md) 因此固定为：跑入口漏洞 → 用 SafeB9SInstaller 装 B9S → 装 Luma3DS（SD 卡根目录 `boot.firm`）。Luma 再以合法签名 FIRM 的身份被 Boot9 加载，去补丁官方系统（详见第二部分和 [Luma3DS](../02-工具百科/Luma3DS.md)）。

**和我们折腾的关系**：

- B9S 装在内部 NAND，**不依赖 SD 卡**——SD 卡丢了、格式化了对破解本身没有影响，换卡只需重建 CFW 文件。这是它和更老方案（emuNAND、Gateway）的本质区别。
- 老教程里的入口漏洞大多已失效，动手前永远以 [3ds.hacks.guide](https://3ds.hacks.guide/) 当前版本为准。
- 备用路线 ntrboot 利用的是 BootROM 里"卡带启动"的合法路径（Bootloader 页有记载），需要烧录卡硬件，是唯一与系统版本完全无关的入口。

三个由此澄清的常见误解：

- **"系统更新会不会把破解更新没了？"**——不会。更新替换的是 NAND 里的官方 FIRM 和系统 Title，B9S 工作在 BootROM 验签之后、官方 FIRM 之前这个更新永远够不着的缝隙里。
- **"删掉 SD 卡上的 `boot.firm` 是不是破解就没了？"**——破解（B9S）还在 NAND 里，丢的只是开机后的 CFW 入口，机器会黑屏；从备份拷回一份 Luma 即恢复。
- **"我把整卡 NAND 备份恢复到另一台机器行不行？"**——不行。NAND 是密文，密钥（movable.sed、OTP 等）逐机唯一，跨机恢复必然无法启动；这也解释了为什么备份和机器必须一一对应保管。

## 二、系统架构速览

### 两侧各有什么

| | ARM9 侧 | ARM11 侧 |
| --- | --- | --- |
| 内核 | Kernel9 | Kernel11（New 3DS 为四核，旧机型两核） |
| 核心进程 | **Process9**：ARM9 唯一的用户态进程，NAND 读写、Title 安装解密、密钥服务等全部系统级操作都经它手 | 系统模块（见下表）、HOME 菜单、游戏进程 |
| 我们眼中的它 | GodMode9、Decrypt9 等工具直接顶替/运行于这一侧 | Luma 的补丁和自制模块主要作用于这一侧 |

ARM11 的系统模块（NATIVE_FIRM 自带，参考 [3dbrew - FIRM](https://www.3dbrew.org/wiki/FIRM)）：

| 模块 | 职责 | 和折腾的关系 |
| --- | --- | --- |
| PM（Process Manager） | 启动/终止进程 | Luma 重实现它来实现断点调试、解除 FS 访问限制 |
| FS | 文件系统服务（SD、NAND 各分区存档） | 存档工具（TYSS/Checkpoint）最终都通过它 |
| SM（Service Manager） | 服务注册与访问控制 | Luma 重实现它来解除服务访问限制 |
| loader | 从存储加载可执行文件 | **Luma 在这里打补丁**：LayeredFS、游戏补丁、区域模拟全是在加载时改写 |
| pxi | ARM11 ↔ ARM9 通信 | 两侧唯一的通道 |
| NS | 系统启动编排、自动启动 Title | 开机进 HOME 菜单的"总导演" |

启动顺序（[3dbrew - Bootloader](https://www.3dbrew.org/wiki/Bootloader) 的 Boot Procedure 一节）：FIRM 加载完成后，ARM11 内核启动各系统模块 → PM 拉起 NS → 无自动启动任务时 NS 通过 PM 启动 HOME 菜单（约 4 秒点亮屏幕，约 7 秒菜单可交互）。Homebrew Launcher 之所以能"伪装成游戏"被启动、Rosalina 之所以能暂停任意进程，都是基于这套进程管理体系。

### 常见折腾组件运行在哪一环

把日常用的东西放回架构图里，很多"为什么"就不言自明了：

| 组件 | 运行的位置 | 权限 |
| --- | --- | --- |
| boot9strap | BootROM 加载 FIRM 之后、官方 FIRM 启动之前 | ARM9，最高 |
| Luma3DS（`boot.firm`） | 顶替/补丁官方 NATIVE_FIRM | ARM9 + ARM11 |
| GodMode9（`.firm` payload） | 由 Luma chainload 启动的独立 FIRM | ARM9，直接读写 NAND |
| Rosalina / LayeredFS | ARM11 系统模块层（补丁 loader 等） | ARM11 内核级，低于 ARM9 |
| Homebrew Launcher + `.3dsx` | ARM11 用户态进程 | 最低，只能碰自己 |
| 入口漏洞（super-skaterhax 等） | ARM11 用户态（浏览器/设置等应用内） | 最低，是跳板不是终点 |

### FIRM：固件镜像与系统版本的关系

FIRM（Firmware Image）是 3DS 的固件容器格式：一个 FIRM 里打包了 ARM9 内核 + Process9 + ARM11 内核 + 基础系统模块，BootROM 验签后整体加载。系统里有好几种 FIRM：

| FIRM | 用途 |
| --- | --- |
| **NATIVE_FIRM** | 3DS 本体模式，装在 firm0/firm1 分区，系统版本号（如 11.17.0-50）本质上就是它的版本 |
| TWL_FIRM | DS/DSi 兼容模式（见 [NDS与GBA](../04-功能模块/45-NDS与GBA.md)） |
| AGB_FIRM | GBA 原生 VC 模式 |
| SAFE_MODE_FIRM | 安全模式，系统更新用 |

系统更新 = 往 NAND 写新版本的 NATIVE_FIRM 及相关 Title；firm0/firm1 互为备份，Boot9 依次尝试直到有一个通过验签。3dbrew 的 FIRM 词条附了每个系统版本对应的 FIRM 内核版本对照表。

**和我们折腾的关系**：

- 系统更新替换的是 FIRM 和各系统 Title，**不会动 B9S**（B9S 抢在官方 FIRM 启动之前），所以破解后正常联网更新通常是安全的——前提是 Luma 保持较新版本（见 [备份与恢复](../01-系统折腾/10-备份与恢复.md) 的安全提醒）。
- CTRTransfer、换区等操作替换的就是 CTRNAND 里的整套系统 Title + FIRM，所以风险高、必须先有 NAND 备份。
- Luma3DS 本身编译出来就是一个 `boot.firm`（[LumaTeam/Luma3DS](https://github.com/LumaTeam/Luma3DS) 源码仓库的自述写得很清楚：arm9/arm11 组件负责补丁官方 FIRM 的 Process9 并注入自制组件，loader 组件负责游戏补丁）。想理解 LayeredFS 到底挂在哪一层，读它的源码比任何教程都直接。

## 三、存储结构：NAND 分区与 SD 卡

参考：[3dbrew - Flash Filesystem](https://www.3dbrew.org/wiki/Flash_Filesystem)、[3dbrew - Titles](https://www.3dbrew.org/wiki/Titles)。

### NAND 布局：一个盘，两个时代

NAND（内部闪存）的前部保留给 DSi 血统的 TWL 世界，后部是 3DS 自己的 CTR 世界。第 0 扇区是 **NCSD 头**：既包含全部 CTR 分区的偏移/大小表，也内嵌 TWL 分区的 MBR 分区表——所以 TWL 分区由 MBR 描述，CTR 分区由 NCSD 头描述。

| 区域 | 分区 | 内容 |
| --- | --- | --- |
| TWL（前 0xB100000 字节） | twln | DSi 模式的系统 FAT16 分区 |
| | twlp | DSi 模式照片 FAT12 分区 |
| CTR | firm0 / firm1 | NATIVE_FIRM 本体与备份 |
| | CTRNAND（`nand:`） | 3DS 系统的 FAT16 分区：系统 Title、`movable.sed`、数据库等 |
| | （隐藏） | GBA VC 存档等专用小分区 |

整个 NAND 用 AES-CTR 加密，不同区域用不同密钥槽（keyslot）；New 3DS 与旧机型、CTR 与 TWL 各用不同的密钥。密文的存在意味着：**NAND 备份离开这台机器就是一堆乱码，解密需要本机密钥**——这正是 `movable.sed`、`boot9.bin`、`essential.exefs` 重要性的根源（备份方法见 [破解后初始化](../00-新手上路/02-破解后初始化.md) 和 [备份与恢复](../01-系统折腾/10-备份与恢复.md)）。

CTRNAND 内部的关键位置（[Flash Filesystem](https://www.3dbrew.org/wiki/Flash_Filesystem) 有完整目录树）：

```
nand:/
├── private/movable.sed   ← 本机主密钥（ID0 的根，见下）
├── dbs/                  ← title.db / import.db / ticket.db / certs.db
├── title/                ← 安装在 NAND 的系统 Title（.app/.tmd/.cmd）
├── data/<ID0>/           ← 系统存档（sysdata、extdata），明文存储
└── rw/、ro/              ← 系统可读写/只读配置（SecureInfo、存档种子等）
```

### SD 卡：`Nintendo 3DS/<ID0>/<ID1>/` 的来历

装到 SD 卡的游戏和数据在 `Nintendo 3DS/<ID0>/<ID1>/` 下，其中：

- **ID0**：`movable.sed` 的 keyY 做 SHA256 后取前 16 字节的十六进制。**它由机器密钥派生，不随卡变化**。
- **ID1**：由 SD 卡自身的 CID（卡序列号）派生，**换卡就变**。

目录下主要内容（结构与 NAND 的 `title/` 相同，见 [3dbrew - Titles](https://www.3dbrew.org/wiki/Titles)）：

| 子目录 | 内容 |
| --- | --- |
| `title/<TitleID高>/<TitleID低>/content/` | 已安装游戏的内容文件：`*.app`（NCCH）、`*.tmd`、`*.cmd` |
| `title/<TitleID高>/<TitleID低>/data/` | 该游戏的存档 `00000001.sav` |
| `dbs/` | SD 侧 title.db / import.db |
| `extdata/` | 额外数据：主题、徽章、游戏附加数据（DISA/DIFF 容器） |

SD 上的 title 数据用本机独有密钥加密，NAND 上则是明文。

**和我们折腾的关系**：

- **这就是"破解后第一步备份 movable.sed"的原因**：它派生 ID0，是解密本机一切数据（NAND、SD 卡内容、存档）的总钥匙。泄露它等于交出整台机器，绝不上传（反复强调见 [备份与恢复](../01-系统折腾/10-备份与恢复.md)）。
- 换 SD 卡：系统发现 ID1 对不上会重建目录，旧数据"认不出来"（看起来空卡），数据其实还在，插回旧卡即恢复；整个 `Nintendo 3DS/` 目录不可跨机通用。
- 二手清理时格式化 NAND 用户数据不动 SD 卡，反之亦然——两边都要清（步骤见 [备份与恢复](../01-系统折腾/10-备份与恢复.md)）。

### Title 数据库与 ticket：安装记录和购买凭证

参考：[3dbrew - Title Database](https://www.3dbrew.org/wiki/Title_Database)、[3dbrew - Ticket](https://www.3dbrew.org/wiki/Ticket)。

NAND 的 `nand:/dbs/` 和 SD 的 `<ID1>/dbs/` 里各有一组数据库（DIFF 容器格式）：

| 文件 | 存什么 |
| --- | --- |
| ticket.db（仅 NAND） | 全部已安装 ticket（购买凭证），见下文 |
| title.db | 已安装 Title 的清单（每个 Title 一行：大小、版本、内容 ID、存档 ID……） |
| import.db | 待完成的安装记录（下载/更新先写到这里，确认完成才转入 title.db） |
| certs.db | 验证 TMD/证书链的证书 |

**ticket（购买凭证）** 决定一个数字版内容"是不是你的"：它里面存着用本机密钥加密的 **titlekey（标题密钥）**，安装和运行时用 ticket 解出 titlekey 才能解密 `.app` 内容。HOME 菜单显示图标的依据是 title.db 里有记录**且** ticket.db 里有对应 ticket。

**和我们折腾的关系**：

- "装了游戏但 HOME 菜单不显示"绝大多数是 ticket 缺失——用 faketik 重建假 ticket 即可让图标回来（见 [FBI](../02-工具百科/FBI.md) 和 [术语表](../00-新手上路/03-术语表.md)）。
- import.db / title.db 损坏会导致已安装内容识别异常，修复手段（GodMode9 重建数据库）见 [备份与恢复](../01-系统折腾/10-备份与恢复.md) 与 [坑与技巧](../01-系统折腾/14-坑与技巧.md)。
- 系统更新、游戏更新的"秒装"体验靠的是 import.db 预写入机制——理解了这一点，就理解为什么更新中断后 import.db 里会留半成品。

## 四、游戏与软件的文件格式速查

折腾中碰到的文件五花八门，其实它们是一条生产链上的不同环节。参考：[3dbrew - CIA](https://www.3dbrew.org/wiki/CIA)、[CCI](https://www.3dbrew.org/wiki/CCI)、[NCCH](https://www.3dbrew.org/wiki/NCCH)、[CXI/CFA](https://www.3dbrew.org/wiki/NCCH)、[ExeFS](https://www.3dbrew.org/wiki/ExeFS)、[RomFS](https://www.3dbrew.org/wiki/RomFS)、[SMDH](https://www.3dbrew.org/wiki/SMDH)、[TMD](https://www.3dbrew.org/wiki/TMD)、[Titles](https://www.3dbrew.org/wiki/Titles)。

### 一张表对照

| 扩展名 | 全称 | 是什么 | 折腾中在哪一步用 |
| --- | --- | --- | --- |
| `.cia` | CTR Importable Archive | 安装包：证书链 + ticket + TMD + 加密内容 + 图标元数据 | FBI 安装的对象；GodMode9 可把卡带转 CIA |
| `.3ds` | CCI（CTR Cart Image）/ NCSD | 卡带整盘镜像（含游戏、手册、更新等分区） | GodMode9 从卡带导出；模拟器/部分工具直接读取 |
| `.cxi` | CTR Executable Image | 可执行 NCCH：代码 + 资源 | CIA/卡带解包后的游戏本体 |
| `.app` | （无统一缩写） | 安装后落到 `title/.../content/` 的 NCCH 内容文件 | NAND/SD 里已安装内容的实际文件 |
| `.tmd` | Title Metadata | 标题元数据：版本、内容清单及各内容 SHA256 | 每个已安装 Title 的 `*.tmd`；CDN 下载索引 |
| `.3dsx` | 3DS Executable（自制格式） | Homebrew Launcher 运行的自制程序 | 放 `/3ds/`，HBL 启动（见 [Homebrew Launcher](../02-工具百科/HomebrewLauncher.md)） |
| `.firm` | FIRM 镜像 | 可引导固件（自制 payload） | `boot.firm`（Luma）、`luma/payloads/*.firm`（GodMode9 等） |
| `.smdh` | 严格说是 icon 数据 | 图标/多语言标题/区域锁信息 | 游戏图标与名称的来源 |

### CIA 里面长什么样

```
CIA = 证书链（CA → Ticket 证书 → TMD 证书）
    + Ticket（含加密的 titlekey）
    + TMD（内容清单 + 各内容 SHA256，由任天堂签名）
    + 内容数据（即 NCCH，用 titlekey 做 AES-CBC 加密）
    + Meta（图标等，可选）
```

安装过程（ARM9 侧 Process9 + AM 服务完成）：验证书链 → 用 ticket 解出 titlekey → 验 TMD 签名、逐内容解密并校验哈希 → 写入 `title/` 目录 → 登记 import.db / title.db / ticket.db。CIAS 与任天堂 CDN 上的内容格式一致，这就是"CDN 内容可打包成 CIA"的原理，也是 [3dbrew - CIA](https://www.3dbrew.org/wiki/CIA) 那句"CIA 能包含 CDN 标题能包含的一切"的含义。

### 卡带镜像（CCI/NCSD）的分区

`.3ds` 文件是 NCSD 容器，最多 8 个分区，零售卡带固定用到其中几个（[3dbrew - CCI](https://www.3dbrew.org/wiki/CCI)）：

| 分区 | 内容 | TitleID 开头 |
| --- | --- | --- |
| NCCH 0 | 游戏本体（CXI） | 0004 |
| NCCH 1 | 电子说明书（CFA） | 0005 |
| NCCH 2 | Download Play 子程序（CFA） | 0006 |
| NCCH 7 | 卡带强制更新数据 | 8000 |

### NCCH 容器：CXI / CFA、ExeFS 与 RomFS

[3dbrew - NCCH](https://www.3dbrew.org/wiki/NCCH)：NCCH（Nintendo Content Container Header）是 3DS 一切内容的通用容器，分两种形态：

- **CXI**（可执行）：NCCH 头 → 扩展头（权限/访问控制）→ ExeFS → RomFS
- **CFA**（不可执行）：手册、DLP 子程序、系统数据档案等

容器内部：

| 部分 | 内容 | 参考 |
| --- | --- | --- |
| ExeFS（可执行文件系统） | `.code`（ARM11 程序本体，可压缩）、`logo`、`banner`、`icon`（即 SMDH 图标） | [3dbrew - ExeFS](https://www.3dbrew.org/wiki/ExeFS) |
| RomFS（只读文件系统） | 游戏资源：模型、贴图、文本、音频…… IVFC 哈希树保证完整性 | [3dbrew - RomFS](https://www.3dbrew.org/wiki/RomFS) |
| SMDH（icon） | 16 种语言的标题、发行商、**区域锁信息**、图标 | [3dbrew - SMDH](https://www.3dbrew.org/wiki/SMDH) |

容器的扩展头、ExeFS、RomFS 用 AES-CTR 加密，密钥由 bootrom 初始化的密钥槽 + NCCH 自身数据派生——没有密钥体系就解不开，这正是 ARM9 权限值钱的原因。

**和我们折腾的关系**：

- **汉化补丁为什么能直接放 SD 卡**：Luma 的 LayeredFS 是在 `loader` 加载游戏时，把 RomFS 里的文件请求重定向到 SD 卡上的同名文件，游戏本体一个字节都不用改（见 [简体中文系统](../01-系统折腾/11-简体中文系统.md)）。
- 区域锁的判断数据就在 SMDH 里，Luma 的区域模拟也是在这一层打补丁。
- GodMode9 能挂载 CIA/`.3ds`/NCCH/ExeFS/RomFS 像浏览文件夹一样浏览（见 [GodMode9](../02-工具百科/GodMode9.md)），转格式、提取 `.code`、导存档全靠这个能力。
- 想自己拆包/打包研究格式：PC 端用 [3DSGuy/Project_CTR](https://github.com/3DSGuy/Project_CTR) 里的 **ctrtool**（读取/解包）和 **makerom**（生成 CXI/CCI/CIA）。
